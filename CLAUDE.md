# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Go web server that lets users query/manage a VMware Avi (NSX ALB) Load Balancer via natural language, backed by an LLM (Mistral AI or Ollama). Gin serves both a JSON API and an HTMX-based server-rendered chat UI.

## Commands

```bash
# Build (compile check only — do not run the resulting binary directly)
go build -o build/bin/aviagent .          # or: make build

# Tests
go test ./...                             # all tests
go test ./internal/avi/...                # single package
go test -run TestName ./internal/avi/...  # single test
make test                                 # verbose, race detector, coverage -> build/coverage/coverage.out
make test-integration                     # tag=integration, ./tests/integration/... (no such dir currently exists)

# Lint / vet / format
go vet ./...
make fmt                                  # gofmt + goimports
make lint                                 # golangci-lint (not installed by default; make setup-dev installs it)

# Run — Docker only
docker-compose --env-file .env up -d --scale ollama=0   # Mistral/python provider, no Ollama container
docker-compose --env-file .env up -d                    # Ollama provider, includes Ollama service
make docker-build / make docker-compose-up
```

**Running the app is Docker-only** — never `go run .`, `make run`, `make run-dev`, or execute the compiled binary directly, even for a quick smoke test. Use the commands above (or check if the dev container from `docker-compose --env-file .env up -d ...` is already running before starting another).

`docker-compose up -d` alone reuses the existing image — only `config.yaml` is volume-mounted, so Go/template/static edits need a rebuild: `docker-compose --env-file .env up -d --build`.

There is no `cmd/server` directory — `main.go` lives at the repo root, so `go build .` (not `go build ./cmd/server`) is correct. Note `make build-all` in the Makefile still references `./cmd/server` and is currently broken; don't trust it without checking.

The Avi MCP server (`mcp-avi-server/`) is a separate npm project, not wired into `make build`/`go build`: `cd mcp-avi-server && npm install && npm run build`. The Go app looks for its compiled output at `mcp-avi-server/build/index.js` (see **Avi MCP server** below) — rebuild it after editing anything under `mcp-avi-server/src/`, the Go side won't pick up source changes.

## Architecture

**Entry point:** `main.go` loads config, builds a `web.Server` (`internal/web/web-server.go`), and runs it behind `net/http` with graceful shutdown.

**Two LLM providers, selected by `config.Provider` (`"ollama"` or `"python"`)** — set in `config.yaml`/`LLM_PROVIDER` env var:
- `"ollama"` → `internal/llm` talks directly to a local Ollama HTTP endpoint.
- `"python"` → `internal/python` (`PythonBridge`) shells out to a Python subprocess (`python3 -m python_mistral.bridge <command> <json>`) which wraps the official Mistral Python SDK (`python_mistral/client.py`). This is the recommended/default provider (more reliable tool-calling than raw Ollama JSON parsing). Go and Python communicate via JSON over argv/stdout, not a long-lived socket — each call spawns a fresh interpreter.
- **Gotcha:** `internal/config/config.go` (`validateConfig`) only accepts the literal strings `"ollama"` or `"python"` for `LLM_PROVIDER`/`provider` — never `"mistral"`, even for the Mistral setup path (`.env.example` and `start-mistral.sh` both write `LLM_PROVIDER=python`, since "python" names the provider *implementation*, not the LLM). An older `.env` with `LLM_PROVIDER=mistral` fails config validation at startup.

Provider selection is threaded through `internal/web/web-server.go` at nearly every handler (`s.config.Provider == "ollama"` branches for history/model-list format, since Ollama and the Python/Mistral bridge use different chat-history and model-list shapes).

**Avi client** (`internal/avi/avi-client.go`): hand-rolled HTTP client against the Avi Controller REST API — session or basic auth (`avi.auth_method`), response caching with TTL, retry logic for transient errors. `internal/avi/avi-client-official.go` (`OfficialClient`, wraps `github.com/vmware/alb-sdk`) is an alternate implementation that exists but is **not wired into `web-server.go`** — the hand-rolled `Client` is what's actually used in `getAviClient()`.

**Tool calling loop:** `processChatMessage` (`web-server.go`) sources tool definitions from `s.getMcpAviClient()` — a lazy-initialized `internal/mcpavi.Client` that spawns `mcp-avi-server/build/index.js` (see **Avi MCP server** below) over stdio and asks it for its tool list. If MCP is disabled (`mcp.enabled: false`) or the subprocess/controller is unreachable, it falls back to the static `internal/llm.GetAviToolDefinitions()` (`internal/llm/tools.go`, 12 hand-written tools covering VS/pool/health-monitor/SE/analytics). Every call goes through `executeToolCall` first — the read-only mode gate (see **Read-only/read-write mode** below) — which then hands allowed calls to `dispatchToolCall` for the actual routing: if the MCP client is connected and `HasTool(name)` is true, the call goes to `mcpAviClient.CallTool`; otherwise it falls through to a switch-case dispatching to `avi.Client` methods (kept intentionally — `internal/tests/virtual_services_e2e_test.go` calls `GetAviToolDefinitions()` directly, and it's the fallback path when MCP is down). `/api/tools/apply` (the explicit unlock path) calls `dispatchToolCall` directly, skipping `executeToolCall`'s gate on purpose. `avi_tools_definition.json` at the repo root is a stale reference export of just the fallback 12 tools, not something the Go code loads at runtime.

**Avi MCP server** (`mcp-avi-server/`, TypeScript, `@modelcontextprotocol/sdk`, stdio transport): comprehensive Avi Controller REST coverage via **generic** tools rather than one hand-written schema per object type — Avi exposes 170+ object types (`ALL_OBJECT_TYPES` in `src/objectTypes.ts`, extracted from a live controller's `/swagger/` index) all following the same `/api/<lowercased-type-name>[/uuid]` CRUD convention. Tools: `avi_list_object_types` (catalog/discovery), `avi_list`/`avi_get`/`avi_create`/`avi_update`/`avi_patch`/`avi_delete` (generic CRUD for any object type), `avi_action` (sub-resource/workflow actions not covered by CRUD — scaleout, scalein, migrate, runtime status, etc. — hits `/api/<type>/<uuid>/<action>`), `avi_get_analytics` (`/api/analytics/metrics/<resource_type>[/<uuid>]`). `src/aviClient.ts` authenticates lazily (on first tool call, not at process start, so the MCP server can start even if the controller is down) via session or basic auth matching `internal/avi/avi-client.go`'s headers/cookies exactly, and re-logs-in once on a 401. Reads Avi connection settings from `AVI_HOST`/`AVI_USERNAME`/`AVI_PASSWORD`/`AVI_VERSION`/`AVI_TENANT`/`AVI_AUTH_METHOD`/`AVI_INSECURE`/`AVI_TIMEOUT` env vars — `internal/mcpavi/client.go` passes these through from `config.Avi` when it spawns the subprocess (single source of truth stays the Go config). Build with `npm run build` in `mcp-avi-server/` (not wired into `make build`); `internal/mcpavi.resolveServerPath()` looks for the compiled bundle at `mcp-avi-server/build/index.js` (local dev, cwd = repo root) or `/opt/avi-mcp-server/build/index.js` (Docker, built in the `node-builder` stage), or override with `mcp.server_path`/`AVI_MCP_SERVER_PATH`.

**Tool result rendering:** every successful tool call result gets appended to the assistant message as an `API Result (<tool_name>):` heading followed by a fenced `json` code block (`processChatMessage`'s tool-call loop in `web-server.go`). A write refused by read-only mode (see **Read-only/read-write mode** below) gets a `WRITE BLOCKED (<tool_name>):` heading instead, with a JSON block carrying `{tool, method, path, body, args}`. `renderChatMessage` (same file) is a hand-rolled line-by-line parser that recognizes both headings, but handles their fenced blocks differently: a `WRITE BLOCKED` block's `.write-refusal-card` wrapper (Unlock-and-apply / Show-details buttons) is written immediately at the *opening* fence, since nothing downstream needs the JSON's content first. An `API Result` block instead defers its `.api-result-block` wrapper, toolbar, and fenced `<pre>` to the *closing* fence — buffering the raw JSON into `jsonBuf` (with the tool name held in `currentBlockTool`) as each line streams by — because only once the full JSON is known can it ask `internal/web/render.ObjectTable()` whether to render a structured table above the (now-collapsed) JSON. If you touch this state machine, keep the two heading-prefix checks and their parenthetical tool-name extraction in sync with `processChatMessage`'s actual heading formats, or the cards/tables stop appearing.

**Structured answer tables** (`internal/web/render/objects.go`): `ObjectTable(jsonText string) string` classifies an `API Result`'s shape by field presence, not by tool name — `avi_list`/`avi_get` (the MCP generic tools, the default path) take the object type as an *argument*, so the tool name alone never tells you what came back. Recognizes `vsvip_ref` or `services`+`cloud_ref` as a virtual service, `lb_algorithm` or `servers` as a pool, `send_interval`+`receive_timeout` as a health monitor, `mgmt_ip_address` as a service engine; each renders a table with fixed columns (e.g. VIRTUAL SERVICE/VIP/HEALTH/CONNS/POOL) built from a JSON list envelope (`{"count":N,"results":[...]}`) or a single object. Returns `""` for anything unrecognized, in which case the fenced JSON (still rendered, just collapsed) is the only view — this fallback is deliberate, not a bug: a hand-rolled `execute_generic_operation` call, or a future Avi object type the classifier doesn't know, degrades gracefully instead of mis-rendering. Missing fields degrade per-cell to `—`, not a blank or an error: a virtual service's `CONNS` column is *always* `—` because live connection counts live on the analytics/runtime endpoints, not the config object being rendered here; `VIP`/`POOL` only resolve to a name if the underlying ref URL carries Avi's `#name` fragment (i.e. the tool call used `include_name`), otherwise `—` rather than a raw UUID. A single pool result additionally gets a nested member table built from its `servers` array, since pool members aren't a listable Avi object type on their own.

**Diagram download:** `renderChatMessage` appends a `.diagram-download-btn` button to every `.api-result-block`'s toolbar regardless of whether a table rendered next to it. `web/static/js/app.js`'s `initializeDiagramDownload()` delegates clicks on that button, reads the adjacent `<pre><code>` JSON (`block.querySelector('pre code')` finds it regardless of a table sitting between the toolbar and the `<pre>`), fetches `web/static/diagram/template.html` (a generalized copy of `prototypes/node-link-diagram/index.html` — same node-link visualization, but "virtual service" wording swapped for neutral "top-level item" since this now renders arbitrary Avi API results, not just VS lists), swaps its embedded `DATA` between the `/*__AVI_DIAGRAM_DATA_START__*/`/`/*__AVI_DIAGRAM_DATA_END__*/` sentinel comments, and downloads the result as a standalone HTML file via a `Blob` + `<a download>`. No backend endpoint involved — generation is entirely client-side.

**Testing Blob downloads in-browser:** chat Export and the diagram download button both use `Blob` + `<a download>`; Claude-in-Chrome can't inspect a real OS save dialog. To verify, monkeypatch `URL.createObjectURL` and `HTMLAnchorElement.prototype.click` before triggering the action, to capture the Blob/filename instead.

**Frontend:** Two UI implementations coexist:
- `web/templates/*.html` + `web/static/{css,js}` — Gin-rendered HTML with HTMX (`/htmx/*` routes), this is what's actually served in production/Docker.
- `web/src/` — a separate React/TypeScript app (`web/package.json`, react-scripts) that does not appear to be built into the Docker image or referenced by the Go server. Confirm which UI a task targets before editing.

Template/static paths are resolved relative to cwd at startup (`internal/web/web-server.go`, `setupRouter`): it checks for `web/templates` vs `templates`, so the binary works both from the repo root (local dev) and from `/web` (Docker `WORKDIR`).

**UI layout:** `web/templates/index.html` is a three-column shell (session rail / conversation / trace inspector) on the "Nocturne" design system (`web/static/css/style.css`'s `:root` tokens — dark-only, OKLCH status hues, Inter + IBM Plex Mono). Bootstrap 5 (CSS+JS) is still loaded and re-themed via CSS variables rather than replaced, to keep `chat.html`'s markup and its `data-bs-toggle="collapse"` JSON-toggle behavior working unmodified.

**Trace inspector & per-turn correlation:** the inspector panel renders `EnhancedLogEntry` records streamed from `/api/logs/enhanced` (SSE; `type`/`level`/`turn` query params filter it) as step rows (`web/static/js/app.js`'s `createLogElement`/`classifyTraceEntry`) — a 4-segment filter (All/LLM/Avi/Errors) plus search, replacing the old type+level `<select>`s. Every log call inside `processChatMessage` and its tool-call loop is stamped with a `turn_id` (generated per `handleHTMXChat`/`handleChat` request, carried through `context.Context` via `contextWithTurn`/`turnIDFromContext` rather than changing the ~37 existing `broadcastOperationLog` call sites' signatures) and surfaced as `EnhancedLogEntry.TurnID`. Each assistant message in `chat.html` carries a `data-turn-id` and a trace-summary chip (`N tools · Dms · M objects`, computed server-side — not "steps", since the panel shows several rows per tool call and a naive step count would visibly disagree with what's on screen); clicking the chip reconnects the SSE stream with `&turn=<id>` to isolate the inspector to that turn (with a "Clear" banner to restore the full stream), and clicking a trace step's title row scrolls to and briefly highlights the originating message — see `initializeTraceFiltering`/`initializeTurnChipLinking` in `app.js`.

**Chat sessions** (`internal/web/session_store.go`): `SessionStore` is a small interface (`Create`/`Get`/`List`/`AppendMessage`/`SetMode`/`Delete`/`DeleteAll`) backed by `JSONLSessionStore` — one `<uuid>.jsonl` file per session under `config.Sessions.Dir` (default `data/sessions`; `SESSIONS_DIR` env var), a header line (`id`, `model`, `mode`, `created`) followed by one `ChatMessage` JSON line per turn. Appends are cheap (`O_APPEND`); the only full-file rewrite is `SetMode` (read everything, write a temp file in the *same directory*, `os.Rename` over the original — not `os.TempDir()`, which would make the rename cross-device). Sessions expire after 30 days, swept lazily wherever they're read (`List`/`Get` both `os.Remove` an expired file rather than returning it) — there's no background sweeper. `handleHTMXChat` resolves the active session from the `active_session_id` cookie (`getOrCreateActiveSession`, HttpOnly, 30-day max-age refreshed on every use) and persists both sides of the turn after a successful response; the JSON `/api/chat` path does **not** persist to a session at all. The rail (`history.html`, also served directly at `GET /htmx/history`/`GET /htmx/sessions`) lists sessions newest-first with a title derived from the first stored message; `POST /htmx/sessions` creates one and returns the rail fragment (read via response headers `X-Session-Id`/`X-Session-Mode` by `app.js`'s `initializeSessionRail`, not parsed from the HTML body); `GET /htmx/sessions/:id` replays one into `#chat-messages` via `session_messages.html`; `DELETE /api/sessions/:id` is a plain `fetch` (not htmx) since it's just a DOM removal, no page swap.

**Read-only/read-write mode:** every session defaults to `sessionModeReadOnly`. `executeToolCall` (`web-server.go`) is the *only* gate in front of `dispatchToolCall` (the actual MCP/Avi dispatch, described in **Tool calling loop** above) — it classifies the call via `isWriteTool` and, if it's a write on a read-only session, refuses before dispatch ever happens. Classification is **content**-aware, not just name-prefix: `avi_create`/`avi_update`/`avi_patch`/`avi_delete`/`avi_action` (the MCP generic tools) are unconditionally writes, `execute_generic_operation` is a write unless its `method` argument is exactly `"GET"`, and an unrecognized tool name defaults to write — a false refusal costs one Unlock click, a false allow bypasses the whole feature, so every default leans toward refusing. A refused call becomes a `*writeRefusedError` carrying the method/path/body `describeWrite` reconstructs from the tool's arguments (mirroring the Avi MCP server's own `/api/<type>[/uuid[/action]]` convention) plus the original `Args`, which `processChatMessage` turns into a `WRITE BLOCKED` card (see **Tool result rendering** above) instead of a normal result. Mode is per-session, flipped via `POST /api/sessions/:id/mode` (`{"mode":"read-only"|"read-write"}`) — the composer's segmented control calls this directly (with a `confirm()` gate only on the read-only→read-write transition), and a refusal card's "Unlock and apply" button calls it then replays the exact tool through `/api/tools/apply`, which re-checks the session's mode server-side rather than trusting the client. `modeFromContext(ctx)` defaults to read-only when nothing set it — true for a pre-Phase-5 session file with no `mode` in its header, and for the JSON `/api/chat` path, which carries no session/mode context at all.

**Observability:** `internal/langfuse` sends LLM interaction traces to a Langfuse instance if `langfuse.enabled` is set; optional, wired in `NewServer`.

**Config:** `internal/config/config.go` uses Viper — defaults set in code, overridable by `config.yaml` and then environment variables (prefix-less binds like `AVI_HOST`, `MISTRAL_API_KEY`, `LLM_PROVIDER`, etc. — see `Load()` for the full env var list). `avi.host`/`username`/`password` are always required regardless of provider.

`.env` is gitignored and, when present, typically holds real dev credentials plus a `SERVER_PORT` that overrides `config.yaml`'s placeholders (`docker-compose.yml` itself defaults `SERVER_PORT` to 8088, not `config.yaml`'s 8083) — check `.env` before assuming `config.yaml` reflects what's actually running.

`docker-compose.yml` mounts a named volume (`aviagent-sessions`) at `/web/data/sessions` for chat session persistence (see **Chat sessions** above) to survive `--build` recreating the container. The Dockerfile pre-creates and `chown`s that directory *before* the volume is declared, not after — a fresh named volume is seeded from whatever already exists at its mount path in the image (root:root otherwise, since the app itself only runs `os.MkdirAll` at startup as `appuser`, uid 1000, which can't write into a root-owned directory Docker creates on the fly).

## Git

Solo project (single maintainer, no team review process). Direct commits and pushes to `main` are authorized — this overrides the global "never push directly to main" rule.

## Versioning

`AppVersion` in `main.go` is shown in the UI header badge and in `/api/health`, and is auto-bumped (patch version) on every commit by a `pre-commit` hook installed at `.git/hooks/pre-commit`. The hook stages its own edit to `main.go`, so a fresh commit always ships a new version without manual bumping. **This hook is not tracked by git** (`.git/hooks` never is) — a fresh clone needs it recreated (or copied from another clone) to get the same behavior.

## Repo layout notes

- `archive/` — old test scripts, logs, and analysis docs deliberately moved out of the way; not part of the active codebase (see `archive/README.md`).
- Root-level `test_*.py`, `test_new_ui.html`, `compare_payloads.sh`, `script.py` — ad hoc manual test/debug scripts, not part of `go test`/CI.
- `internal/tests/virtual_services_e2e_test.go` — E2E-style test using `httptest`, in its own `tests` package.
- `monitoring/` — Prometheus/Grafana config for the optional `docker-compose --profile monitoring` stack.
- `api_answer_model.json` (repo root) — a sample Avi `virtualservice` API response, used as fixture data by the node-link-diagram prototype below. Not loaded by the Go server.
- `prototypes/node-link-diagram/index.html` — standalone, self-contained (no build step, no dependencies, `api_answer_model.json` embedded inline) canvas visualization prototype exploring how to present Avi API responses. Renders the JSON as an interactive node-link graph on a radial layout that eases into place. The response envelope is deliberately **not** drawn: `API Response` (which only holds `count` and `results`) and the `results` array itself carry no information worth a ball, so the eight virtual services *are* the top level. Both nodes still exist in the tree — paths, refs and `raw` subtrees resolve through them — but `HIDDEN`/`TOP_NODES` route layout, links, the search index, breadcrumbs and arrow-key navigation around them; the `count` leaf is dropped from search too, since it has no ball to reveal and restates the header's VS count. Leaf/scalar values are never drawn as balls — they live in the right-hand detail panel, which is the load-bearing consequence for anything that navigates: a search hit on a *value* has no ball to fly to, so it resolves to the leaf's **parent** ball and flashes the matching field row. Key interactions: single click selects + expands (it never collapses — that is double-click, or the `−` button in the panel header, so re-reading an open ball can't destroy the subtree you just opened); `/` or ⌘K opens a search over every key, value and path, with live yellow rings on matching balls; arrow keys walk parent/child/siblings; the toolbar has **Expand VSs** (one level under each virtual service, ~123 balls) and **Expand all** (every depth, 269 balls — only containers become balls, so "everything" is a few hundred, not the 792 values); `F` fits, `X` toggles cross-refs, `D` toggles focus mode (dims everything outside the selection's ancestors, children and refs). The panel's breadcrumb, nested-ball chips, and `*_ref` values are all clickable jump targets. A toggleable cross-reference overlay links balls whose fields share a UUID — resolved refs (the UUID matches another listed object's own `uuid` field, e.g. `vh_parent_vs_ref`) draw straight to that ball, unresolved refs (`pool_ref`, `se_group_ref`, etc., pointing at objects not present in this JSON) get a dedicated synthetic "external object" ball instead, ringed in a collar around its owner and de-overlapped by a relaxation pass. **Gotcha for any new navigation code:** `computeRadialLayout()` only assigns `targetX`/`targetY` to descendants of *expanded* nodes, and `focusOn()` reads those — so always expand ancestors → `rebuildVisible()` → *then* move the camera, or you pan to stale/NaN coords with no error thrown (`revealNode()` already does this in the right order; reuse it). A second one: the link render runs a two-pass dim/bright loop keyed on `focusSet`, and pass 0 is the *dim* pass — with focus mode off nothing is dimmed, so that pass must be skipped entirely (`focusSet ? [0, 1] : [1]`) or no structure links draw at all. **Palette:** built in OKLCH and validated with the `dataviz` skill's six checks (`scripts/validate_palette.js`), not hand-picked — neutrals are one hue family (264°) stepped evenly in lightness, and the three ball hues (blue `--n-vs` / rose `--n-object` / amber `--n-array`) sit at near-equal lightness. That triad is a measured result: green and teal collapse against the rose under protanopia/deuteranopia (ΔE 3.0–5.8), so warm-amber is the only viable third hue. Balls are validated **all-pairs** (they're scattered marks, any two can touch): worst CVD ΔE 11.5, normal-vision 17.2. The panel's value-type dots are a *secondary* channel validated adjacent-only — each sits beside its key and literal value, so identity is never colour-alone. Re-run both after any colour change. Not wired into the Go server or `web/` build — open `index.html` directly, or serve it with any static file server (`python3 -m http.server`) since some tooling blocks `file://` URLs.
- `prototypes/avi-mcp-server/index.html` — standalone, self-contained showcase page for the `mcp-avi-server/` MCP server (see **Avi MCP server** above): why nine generic tools cover all 170 Avi object types, the REST shape they all share, a real (not mocked) tool-call transcript, and a categorized coverage list. Not wired into the Go server or `web/` build — open directly, or serve with `python3 -m http.server`. Kept deliberately under ~13KB total: Claude Artifacts (where this page was designed and published) has an undocumented hard rendering-failure threshold around that size — confirmed by padding a working file with inert HTML comments alone — so avoid growing this file past that without re-verifying on the Artifacts platform if republishing there.
